02. Propósito y filosofía del laboratorio

Este laboratorio responde a una necesidad muy concreta: tener un entorno bajo control donde ensayar un Blue Team / SOC operativo — ingestión de logs, detección de intrusiones, honeypots expuestos y capacidad de respuesta. Nada de papel: está corriendo, captura tráfico hostil real y sus alertas aterrizan en Telegram.

Tres principios gobiernan cada decisión de diseño:

  1. Aislamiento estricto: ningún servicio administrativo se asoma a internet; el acceso viaja siempre por la VPN privada sobre Tailscale.
  2. Infraestructura como Código (IaC): cada componente queda definido en Terraform y configurado con Ansible — reproducibilidad total y documentación que nunca caduca.
  3. Defensa en profundidad: anillos concéntricos de logs, contenedores sin privilegios, firewalls con inspección profunda y segmentación de red para acorralar cualquier compromiso.

03. Infraestructura base: Home, SOC/NOC y Honeypot Core

VM local «Home» — el centro de control

El proyecto arranca en una máquina virtual local con Debian 13 XFCE apodada «Home». Desde ella administro todo el laboratorio, con una regla innegociable: ningún puerto de administración mira a internet. Las VPS solo se tocan a través de la red privada de Tailscale.

RecursoCPU 4 núcleos · RAM 4 GB · Disco 60 GB · Debian 13 XFCE · 10.100.50.2 · rol: centro de control, IaC y revisión de logs

VPS «SOC/NOC» — el cerebro que vigila

Primera VPS: todo el músculo analítico. Wazuh Manager para SIEM/IDS, Zabbix Server para disponibilidad, Prometheus para métricas y Grafana como panel unificado. Desde aquí salen las alertas hacia la API de Telegram Bot.

VPS «Honeypot Core» — los señuelos

Segunda VPS: el framework T-Pot con sensores multiplataforma (Cowrie, Dionaea, Honeytrap) ofreciendo servicios trampa a internet. Todo el tráfico malicioso viaja de manera unidireccional hacia el SOC/NOC.

Regla de oro: acceso unidireccional

Entre ambas VPS el tráfico solo fluye en un sentido: del Honeypot hacia el SOC/NOC llevando logs. En dirección contraria no existe camino alguno. Si el Honeypot cae en manos de un atacante, este no podrá pivotar hacia el SOC/NOC ni tocar los históricos.

04. Conectividad: Tailscale como tejido conector

Tailscale es la costilla que sostiene toda la estructura: una red privada tipo mesh sobre el segmento 10.100.50.0/24, con IP fija por nodo.

Tailscale sidecar proxy con Podman rootless

Un detalle crítico es dónde vive Tailscale dentro de las VPS: no se instala sobre el sistema operativo, sino dentro de un contenedor Podman en modo rootless actuando como sidecar proxy. Ventajas triples:

  • Abstracción de red: el contenedor tapa las IPs reales de los servidores, incluso ante mis propios ojos: quien entra por Tailscale jamás ve la IP física de la VPS.
  • Aislamiento de privilegios: Podman corre bajo un usuario sin poderes, lejos de la interfaz de red real del host.
  • Redirección interna: el sidecar opera desde la red privada del servidor y deriva el tráfico hacia cada servicio sin exponer interfaces físicas.

Los perfiles administrativos con menos privilegios se conectan a esa instancia embotellada en Podman, y ella les abre únicamente los servicios que necesitan: ven un espacio confinado dentro de una red privada, sin atisbo del sistema operativo subyacente.

05. Diagrama de arquitectura lógica

El plano maestro: flujo completo de datos, direccionamiento IP e interconexión de todas las piezas. Fruto de varias iteraciones, refleja fielmente el despliegue vigente.

Desglose del diagrama

1. Entorno de simulación e ingesta forense (Proxmox VE):

  • Hipervisor protegido: Proxmox VE bajo 10.100.50.30 de la red Tailscale.
  • VM OPNsense (firewall): IP interna 192.168.10.1. Recibe internet por la WAN dedicada 203.0.113.88, aplica DPI, NAT y port forward aislado hacia los señuelos.
  • VM T-Pot Suite: IP interna 192.168.10.100. Sensor multiplataforma (Cowrie, Dionaea, Honeytrap) junto a agentes de Wazuh y Zabbix; logs crudos hacia el Proxy Server.
  • VM Proxy Server: IP interna 192.168.10.5. Colector y balanceador unidireccional que extrae los datos fuera del entorno simulado rumbo al SOC/NOC.

2. Capa de orquestación y red mesh VPN (Tailscale 10.100.50.0/24):

  • VPS SOC/NOC: ingiere logs de forma asíncrona y unidireccional. Aloja Prometheus (métricas), Wazuh Manager (SIEM/IDS), Zabbix Server (disponibilidad) y Grafana (dashboard unificado). Alertas → Telegram Bot API.
  • VPS Honeypot Core: confinada mediante contenedores Podman rootless y abstrae su red física con el Tailscale sidecar proxy.

3. Entorno de control central (local):

  • VM Home: centro de operaciones local. Gobierna la infraestructura con IaC —Terraform, Ansible, PyInfra—, accede por SSH exclusivamente vía red privada y mantiene un servidor de logs local para auditorías.

07. Anillos de logs: defensa en profundidad

La estrategia de logging se organiza en anillos concéntricos, desde lo más externo (cada contenedor) hasta lo más interno (la VPS entera). Si un anillo cae o es manipulado, los demás siguen escribiendo.

Honeypot Core — 4 anillos:

  1. Contenedores de servicios (Podman): logs de cada sensor del T-Pot y del sidecar Tailscale.
  2. Instancias de Proxmox: logs de las VMs del hipervisor.
  3. Contenedor de Tailscale: logs del proxy sidecar y del tráfico de red.
  4. VPS completa: logs del SO, accesos SSH y eventos de seguridad.

SOC/NOC — 2 anillos: (1) contenedores de Tailscale y SOC/NOC; (2) VPS completa.

Home — 1 anillo auto-hospedado: la VM completa con servidor de logs local.

📜
La lección de Oldsmar y Ucrania

Oldsmar (2021) y el apagón de Ucrania (2015) dejaron una certeza incómoda: sin logs resulta imposible distinguir un error técnico de un ataque deliberado. Los anillos de este laboratorio existen precisamente para que esa distinción esté siempre al alcance: cuando algo falla, sé qué anillo debió registrar el evento y puedo seguirle el rastro hasta el origen.

La Infraestructura como Código es uno de los pilares: todo componente está declarado en archivos versionables, capaces de reconstruir el entorno desde cero en minutos.

La API de Contabo como botón de emergencia

La VPS Honeypot se gestiona desde el SOC/NOC a través de la API de Contabo: snapshots antes de cualquier cambio, reinstalación desde cero si detecto compromiso, y apagado del servidor en emergencia — todo desde scripts automatizados.

IPs adicionales para segmentar servicios

Cada servicio expuesto a internet —como los señuelos— recibe una IP adicional propia, distinta de la IP administrativa de la VPS: el tráfico público queda separado por completo de la superficie de gestión.

10. Lecciones aprendidas y próximos pasos

  1. Tailscale simplifica lo complejo: una red VPN segmentada con proxies sidecar habría sido un proyecto en sí mismo; su facilidad no cuesta seguridad si va acompañada de contenedores rootless.
  2. Podman rootless no es un lujo: ejecutar Tailscale sin privilegios añade el colchón de aislamiento que marca la diferencia si el proxy cae comprometido.
  3. IaC es documentación viva: los ficheros de Terraform y Ansible describen el sistema mejor que cualquier wiki, porque son exactamente lo que se ejecuta.
  4. Los anillos de logs no son opcionales: apostar a un único punto de logging es sembrar un desastre forense; redundar la captura de eventos es inversión, no gasto.
  5. Las alertas cierran el bucle: dashboards preciosos valen cero si nadie mira la pantalla; Telegram garantiza que los incidentes se enteren de mí aunque yo no me entere de ellos.

Próximos pasos: centralizar secretos con Hashicorp Vault · migrar playbooks a Mitogen · sembrar Canarytokens como señuelos internos · documentar el ciclo de respuesta a incidentes (de la detección en Grafana a la contención) · explorar MISP para compartir threat intelligence.
