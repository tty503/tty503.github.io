01. Retomando el camino

Hace unas semanas publiqué SAINT GRAIL, la plataforma modular para investigación ofensiva hecha en Python con Flask, SurrealDB y un agente híbrido DeepSeek + DeepWiki. El prototipo era funcional, pero rápidamente se topó con los límites del enfoque: al escalar vectores, nodos y datos JSON entre módulos, el cuello de botella se hizo evidente. Latencia de serialización, consumo de memoria y la imposibilidad de paralelismo real (GIL) empezaron a frenar el ciclo de investigación.

La respuesta fue Go — no por moda, sino por razones técnicas muy concretas. Y los resultados no tardaron.

🔁
Contexto

Este es la continuación directa de SAINT GRAIL: una plataforma modular para investigación de seguridad ofensiva con IA. Si no has leído el anterior, te recomiendo hacerlo para entender el origen.

02. ¿Por qué migrar a Go?

Reescribir el orquestador implicó cientos de líneas, adaptar la concurrencia y rediseñar la interacción con la base de datos. Los beneficios superaron el esfuerzo:

  • Rendimiento en serialización JSON: Python convierte cada clave en dict dinámico; Go, con structs tipados, parsea y rearma JSON hasta 15 veces más rápido, reduciendo la latencia en el intercambio de nodos y aristas entre agente y API.
  • Concurrencia nativa sin bloqueos: las goroutines consumen ~2 KB y ejecutan miles de tareas simultáneas sin overhead de hilos: decenas de vectores en paralelo, consultas DeepWiki mientras corren PoCs y sync P2P sin bloqueos.
  • Menor consumo de memoria: entre 60% y 70% menos RAM que Python en alto volumen — crítico al ejecutar Ollama/Llama 3.2B en la misma máquina: libera recursos para la inferencia del LLM.
  • Parser AST eficiente: con tree-sitter, extrae contexto de código fuente (funciones, dependencias, comentarios) en menos de 4K tokens, reduciendo alucinaciones y acelerando la validación de DeepWiki.
  • Binario único y portabilidad: Go compila a un solo binario estático sin dependencias de Python — despliegue de workers P2P sin líos de versiones de librerías.

Go convierte el orquestador en un motor de alto rendimiento que libera CPU y RAM para lo que importa: la inteligencia del agente y la ejecución de exploits.

03. Arquitectura en Go

Misma filosofía modular, mucho más desacoplada: el orquestador central (orchestrator.go) coordina todos los subsistemas mediante canales y goroutines.

go
// Estructura simplificada del orquestador en Go
type Orchestrator struct {
    store       storage.GraphStore
    llm         llm.Router        // enruta entre DeepSeek, Ollama, etc.
    deepwiki    *deepwiki.Client
    fuzzing     *fuzzing.Fuzzer
    executor    *executor.BinaryExecutor
    tracker     *utils.ExploitTracker
    vectorSem   chan struct{}     // semáforo para concurrencia
    wg          sync.WaitGroup
}
  • Router LLM: múltiples proveedores (DeepSeek, Ollama, pronto Claude) con conmutación en caliente.
  • Parser AST: tree-sitter para C++ y JavaScript, extrayendo contexto relevante de los repositorios objetivo.
  • Fuzzing inteligente: mutación guiada por patrones CVE y feedback de cobertura (cuando está disponible).
  • Executor: ejecuta binarios con entradas tipo stdin/file/argv y detecta crashes por señales y ASAN.
  • Exploit Tracker: registra el progreso RCE → SBX → LPE por target, con ventanas de reintento y persistencia.

El bucle principal opera en ciclos de 5 segundos ejecutando en paralelo: escaneo de PoCs/logs, procesamiento de vectores pendientes (DeepWiki + LLM), fuzzing automático, pruebas de primitivas y calibración de prompts. Cada target se procesa de forma independiente; el semáforo vectorSem limita la concurrencia para no saturar el sistema.

04. Resultados concretos: dos PoCs funcionales

La migración no solo mejoró el rendimiento: el sistema generó dos pruebas de concepto funcionales, descubiertas automáticamente durante los ciclos de investigación/fuzzing y validadas manualmente después.

PoC #1: TOCTOU en el DownloadManager de Chromium

Vulnerabilidad: condición de carrera TOCTOU (time-of-check-time-of-use) en el gestor de descargas. Dos descargas con el mismo nombre, iniciadas casi simultáneamente, pueden colisionar y hacer que una trunque a la otra: Chromium reporta ambas como completadas, pero en disco solo queda un archivo.

Impacto: suplantación de archivos descargados — un atacante puede reemplazar un binario legítimo por uno malicioso durante la descarga y la víctima lo ejecutará confiando en el gestor.

Cómo lo encontró: el agente identificó la ventana de sincronización entre el hilo UI y el hilo de descarga vía parser AST + análisis del flujo; generó el vector, validó con DeepWiki y creó un PoC en Python que demostraba la colisión.

⏱️
Nota sobre la inestabilidad

La carrera depende del timing y la carga del sistema. Con SSD rápido la colisión es menos probable; en HDD o con payloads grandes (50 MB+) la probabilidad aumenta significativamente.

PoC #2: CRC bypass + SFX en 7-Zip

Vulnerabilidad: bypass de integridad (CRC) en el formato 7z. Eliminando el bloque kCRC del header, la bandera CrcDefined pasa a false y la extracción corre sin verificar el CRC. Combinado con el mecanismo SFX, se ejecuta código arbitrario al ejecutar el autoextraíble.

Impacto: ejecución de código asistida por el usuario (user-assisted RCE) y persistencia a nivel de usuario (Startup folder). Afecta 7-Zip 9.20 – 25.01 en Windows.

Cómo lo encontró: durante un ciclo de fuzzing sobre el formato 7z, el agente generó un archivo malformado que pasaba 7z t; al analizar el código fuente vía DeepWiki + AST identificó que el CRC del folder se omitía sin el bloque kCRC, y construyó automáticamente un SFX con el payload embebido.

El bypass de integridad permite distribuir un archivo malicioso que parece legítimo, y SFX asegura la ejecución sin interacción adicional; la persistencia en Startup convierte el ataque en una amenaza duradera, ideal para spear-phishing o droppers.

✅
Validación en vivo

Ejecuté poc_7zip.py en Debian y generó un KB5012345_Installer.exe que, al ejecutarse en Windows, lanza calc.exe. El .7z embebido pasa 7z t sin errores.

06. Explicación detallada de los PoCs

Chromium TOCTOU: anatomía de la carrera

El PoC explota la separación entre el hilo de UI (decide el nombre del archivo) y el hilo de descarga (lo crea físicamente). En condiciones normales, si el archivo existe Chromium añade sufijos incrementales (1), (2)… El fallo aparece cuando dos descargas con idéntico nombre pasan la verificación al mismo tiempo.

  1. Se inyecta un HTML con dos <a> ocultos en iframes, ambos apuntando a descargas diferentes con el mismo atributo download.
  2. Mediante BroadcastChannel se sincronizan ambos contextos: cada iframe confirma que está listo y dispara el clic al recibir la orden.
  3. Ambas descargas arrancan en el mismo instante, sorteando la verificación de existencia y forzando la colisión en DownloadFileImpl::Initialize.
  4. Se monitorizan los eventos vía Chrome DevTools Protocol (CDP) para contar cuántas se reportan completadas y cuántos archivos reales aparecen en disco.
javascript
// Fragmento del HTML inyectado: sincronización vía BroadcastChannel
const bc = new BroadcastChannel("race");
bc.onmessage = (e) => {
  if (e.data === "FIRE") {
    document.getElementById("d").click();
  }
};

Métrica de éxito: CDP reporta ≥2 descargas completadas pero en disco hay exactamente 1 archivo. Se verifica el SHA256 del superviviente: si corresponde al payload malicioso (B), la suplantación es efectiva.

7-Zip CRC bypass: disección del formato y el parche

El formato 7z organiza la información en bloques: el NextHeader define los folders (unidades de compresión) y, opcionalmente, un bloque kCRC con el CRC32 esperado de cada folder.

  1. Localizar el bloque kCRC en el NextHeader: identificador 0x0A seguido de un byte (0x01 = todos los folders comparten CRC, 0x00 = vector de bits).
  2. Eliminar el bloque completo (identificador + flags + datos). El array FolderCRCs queda vacío y CrcDefined = false.
  3. Recalcular los CRCs del header para que el archivo siga siendo sintácticamente válido: NextHeaderCRC (CRC32 del nuevo header) y StartHeaderCRC (CRC32 de los bytes 12-31).
python
# Fragmento del parche: eliminación de kCRC y recálculo
pos = header.find(b"\x0a\x01")  # Caso AllAreDefined=1
if pos >= 0:
    del header[pos:pos+6]   # NID(1) + flag(1) + CRC32(4)
# Recalcular NextHeaderCRC
next_crc = calc_crc32(header)
struct.pack_into("<I", new_data, 28, next_crc)

Tras el parche, 7z t devuelve OK (la estructura sigue siendo correcta). Al extraer, _calcCrc se evalúa como false y la verificación nunca corre: CloseFile() devuelve S_OK aunque los datos no coincidan con el CRC original (inexistente).

Construcción del SFX malicioso

Para pasar de la debilidad a ejecución de código se usa el modo SFX: un ejecutable formado por tres partes concatenadas:

  1. Stub SFX (7z.sfx): un PE pequeño con la lógica de extracción.
  2. Archivo .7z parcheado: el payload empaquetado sin CRC.
  3. Config SFX: bloque de texto con RunProgram y, opcionalmente, Directory para persistencia.
python
# Construcción del SFX en el PoC
with open(output_exe, "wb") as f:
    f.write(stub_data)          # 7z.sfx
    f.write(archive_patched)    # .7z sin CRC
    f.write(sfx_config)         # RunProgram="payload.bat"

La opción --persistence cambia la config para incluir Directory="%APPDATA%\...\Startup": el payload se copia a la carpeta de inicio automático, garantizando ejecución en cada arranque.

🧬
Nota sobre la cadena de explotación

Bypass de integridad + SFX permite distribuir un «instalador de seguridad» que extrae y ejecuta código arbitrario sin levantar sospechas: sin modificar tamaños ni estructura de directorios, el .7z contenido es indistinguible de uno legítimo a nivel de firma.

Ambos PoCs están públicos en saint-grail-pocs-output, con scripts completos, instrucciones y referencias a las secciones exactas del código fuente de Chromium y 7-Zip que confirman las vulnerabilidades.

07. Estado actual y próximos pasos

La versión Go es funcional y ha demostrado su capacidad generando dos PoCs reales. Áreas en marcha:

  • Modelos locales uncensored: rama con Dolphin-Mistral via Ollama para generar exploits sin censura, reduciendo la dependencia de APIs externas.
  • Memoria persistente con Qdrant: vectores embebidos para payloads exitosos y patrones de crashes, con aprendizaje de experiencia pasada.
  • Calibración automática de prompts: calibrator.go ajusta prompts según los fallos de los PoCs.
  • Frontend: migración del grafo/dashboard a SPA React + D3 (el HTML/JS actual sigue funcionando).

Desafíos pendientes de mayor calado:

  • Detección en tiempo real ante nuevos commits de los repos objetivo (hoy: ciclos programados).
  • Fuzzing guiado por cobertura con AFL++ o libFuzzer para dirigir mutaciones a zonas no exploradas.
  • Explotación automática de cadena completa (RCE → SBX → LPE): el encadenado de primitivas hoy es manual; se está diseñando un módulo que las una.
  • Más fuentes de inteligencia (CVE feeds, boletines, exploit-db) además de DeepWiki.
  • RL (DreamerV2) experimental: ajustar función de recompensa y entorno para priorizar vectores prometedores.
  • Red P2P robusta: autenticación, cifrado E2E y reequilibrio de carga entre workers.
  • Pruebas de estabilidad de varios días, documentación type wiki y auditoría/cumplimiento corporativo.

Objetivo a medio plazo: publicar el código completo como open-source cuando la documentación y los tests cubran lo crítico. Mientras tanto, el repo de PoCs y el blog son el canal.
