02. La doctrina de caza

El motor detrás de estos hallazgos no es un fuzzer genérico ni un escáner: es un pipeline multicapa con agentes de IA local que clasifica, audita, valida y documenta. La regla de oro es brutalmente simple: sin crash reproducible no hay hallazgo. Y el error de raíz que se corrigió fue la tentación del análisis estático puro (leer código y opinar) frente a la ingeniería inversa real (construir inputs que rompan el programa).

txt
# Las tácticas de caza que alimentaron los sinks de esta serie
T1  CVE→Variant Sweep  : tomar un CVE reciente, entender el fix, cazar la misma clase en otros paths
T6  Helpers adjacent    : el core se endurece; los binarios de un solo propósito casi nunca
T7  pppd/scripts admin  : scripts que el daemon ejecuta con campos del protocolo sin sanear
T8  Trust-bypass family : headers/cookies de proxy → todos los sinks post-auth se vuelven candidatos
T9  LTS embedded        : la rama dormida que master ya parcheó
T10 Heritage protocol   : bugs de 1994 copiados durante 30 años sin ser rehechos

Cada hallazgo de la serie nació de uno de estos patrones. el daemon de portal cautivo y la suite el panel web de administracion del servidor/el panel web de administracion restringida son T8 (confianza en la cadena EAP→RADIUS→script y en headers de proxy). el daemon de autenticacion y redireccion y el spooler de impresion son T7/T6 (scripts admin y helpers). La IA local procesa cientos de proyectos en paralelo y propone, pero la validación con sanitizers y la construcción de la cadena completa es lo único que separa un crash de un hallazgo. El sistema que lo ejecuta se documenta en la serie Sherlock.

03. El pipeline de validación E2E

El estándar para considerar "demostrado" un hallazgo es el SOP de evidencia E2E en container. Nada de "el código se ve vulnerable": cada fase de la cadena deja un marker y un log que se puede re-verificar. El patrón se aplicó igual en el daemon de portal cautivo, el daemon de autenticacion y redireccion y el servidor HTTP embebido.

bash
# La estructura canónica de validación (abreviada)
docker run -it --name <target>-e2e debian:12 bash
# 1. instalar deps, clonar y compilar el target (con ASAN en los C)
# 2. escribir la suite que ejecuta la cadena y deja markers por fase
#    .m_s01 .. .m_sNN  = cada eslabón (leak→write→control→pivot→log)
# 3. capturar suite_output.log como evidencia final
# 4. verificar el escenario REAL de deployment y el usuario del RCE
SUITE_RCE_DEFAULT=usuario_al_que_llega    # p.ej. el daemon de portal cautivo:1000
SUITE_PIVOT_LOG=usuario_al_que_pivota     # p.ej. root:0

Dos salidas del pipeline merecen mención por lo que enseñan. Un helper setuid root eleva el euid de un binario ELF pero no de un script con shebang, porque el kernel preserva el real_uid del intérprete; eso definió si un hallazgo terminaba en root o no. Y en el servidor HTTP embebido, la dirección del stack difirió en +0xC0 bytes entre correr bajo ptrace (gdb) y correr nativo, y solo se resolvió reconstruyendo el layout en el run real.

04. Primitivas vs productos: el umbral real

Una pregunta recurrente al evaluar estos hallazgos es si una librería (la biblioteca cliente del protocolo de streaming, el servidor HTTP embebido) tiene el mismo valor que un producto. La línea divisoria honesta no es "es librería" ni "es producto", sino "¿puedo demostrar ejecución de código en un escenario de despliegue real donde el código vulnerable sea alcanzable?".

  • RCE real demostrado (ejecución de código, no solo crash): el daemon de portal cautivo (touch uid 0/1000), el daemon de autenticacion y redireccion (reverse shell root), el servidor HTTP embebido (reverse shell low-priv), el panel web de administracion del servidor cpan (reverse shell), el daemon de tunel L2TP/IPsec (markers root), el spooler de impresion (id/touch como lp).
  • Primitivas de solo lectura / N-day sin cadena a RCE: la biblioteca cliente del protocolo de streaming (OOB read AMF3, familia de CVE previos), el servidor HTTP minimo OOB read (heap underflow).

el daemon de portal cautivo rindió una cadena completa con ejecución verificada; la biblioteca cliente del protocolo de streaming solo un leak. Esa diferencia —cadena a RCE frente a primitiva sin completar— define el interés real del hallazgo.

05. Los posts individuales

Cada hallazgo tiene su análisis completo, con el sink línea a línea, PoCs y evidencias E2E.

  • el daemon de portal cautivo: RCE vía EAP-Identity → conup (CWE-78) — Un payload en el primer paquete pre-auth del handshake 802.1X viaja EAP→RADIUS→script sin sanitizar y acaba en un eval. RCE root o low-priv según deployment.
  • el daemon de autenticacion y redireccion: RCE root vía cabecera Host (CWE-78) — Un único request HTTP pre-auth con Host malicioso termina en un execvp("/bin/sh","-c") que construye iptables. Reverse shell root.
  • el servidor HTTP embebido: stack overflow en el conversor de fecha a timestamp (CWE-121) — Un header If-Modified-Since de 220 bytes desborda buf[128] y toma control del RIP con un decoder XOR in-stack.
  • la biblioteca cliente del protocolo de streaming AMF3 + el servidor HTTP minimo el gestor de credenciales — Dos primitivas reales: OOB read N-day en el decoder AMF3 y command injection CLI en el gestor de credenciales, con su cadena y limitaciones.
  • Suite el panel web de administracion del servidor/el panel web de administracion restringida/el daemon de tunel L2TP/IPsec/el spooler de impresion — Cuatro sinks de la familia de scripting servers + L2TP y el spooler de impresion, con el trust-bypass X-SSL-Client-* y su corrección de honestidad.
