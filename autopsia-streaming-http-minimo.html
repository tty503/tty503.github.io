02. Caso A — la biblioteca cliente del protocolo de streaming: OOB read en AMF3

la biblioteca cliente del protocolo de streaming es la librería del cliente RTMP que usa el volcador de flujos del protocolo y, a través de él, la mayoría de reproductores y utilidades de streaming. RTMP encapsula mensajes AMF y el tipo 0x14 es AMF3 INVOKE. El parser de estructuras AMF3 lee valores con un rango mal acotado y produce una lectura fuera de límites (CWE-125).

c
// AMF3_ReadNumber / AMF3_ReadString: lectura sin validar el rango
double AMF3_ReadNumber(AMFObject *obj) {
    // avanza el buffer según la longitud declarada sin comprobar
    // que quede dentro del payload => OOB READ (CWE-125)
}

// Vía de entrada: un servidor RTMP malicioso envía packet type 0x14
// (AMF3 INVOKE) con una longitud que empuja la lectura fuera del buffer
packet_type = 0x14;  // AMF3 invoke, from server -> client

El desencadenante es que el cliente (el volcador de flujos del protocolo/aplicación) procesa un mensaje del servidor RTMP. El resultado es fuga de memoria del heap y, en el mejor caso, crash del cliente; no hay una cadena directa a ejecución de código en las compilaciones típicas. Además, esta zona repite un patrón ya corregido en la misma librería (la familia de bugs previos de la biblioteca cliente del protocolo de streaming), así que es variante de una clase conocida.

⚠
Alcance real

Primitiva de fuga en el lado cliente, alcanzable solo contra una aplicación que se conecte a un servidor RTMP malicioso. No escala a RCE y es variante de un patrón ya corregido.

03. Caso B — el servidor HTTP minimo: el gestor de credenciales command injection

el servidor HTTP minimo es un servidor HTTP mínimo muy usado en sistemas embebidos y routers. Distribuye junto al daemon utilidades auxiliares — entre ellas el gestor de credenciales, que genera los ficheros de autenticación. El argumento (normalmente el nombre del fichero de passwords) llega a un system() sin validar:

c
// el gestor de credenciales.c:214-215 — el argumento del usuario se inyecta en un comando
sprintf(command, "cp %s %s", argv[1], ...);   // argv[1] sin validar
system(command);                    // /bin/sh -c "cp <argv[1]> ..."

// Con argumento ";touch /tmp/pwned;#" se inyecta ejecución local
./el gestor de credenciales ";touch /tmp/pwned;#"   # command injection local

Es un command injection real: el input del usuario llega a sh -c. La limitación crítica es que el gestor de credenciales es una utilidad de línea de comandos local — no un daemon que escuche. Para explotarla, un atacante ya necesita ejecución local en el sistema, o un CGI/helper que derive su invocación de input remoto — que no es el patrón de despliegue por defecto.

⚠
Alcance real

Inyección genuina pero con superficie local: requiere un deploy donde un helper invoque el gestor de credenciales con input influenciable, o acceso local previo. No es alcanzable desde internet contra el daemon por defecto.

04. Primitiva vs impacto

Lo que enseñan estos dos casos — y el resto de la serie — es que la gravedad de un hallazgo no depende solo de la clase (CWE), sino del encadenamiento a ejecución de código y del despliegue real:

  • la biblioteca cliente del protocolo de streaming es un bug real de lectura fuera de límites que se queda en fuga/crash del cliente, sin camino a RCE.
  • el servidor HTTP minimo el gestor de credenciales tiene inyección de comandos real, pero solo alcanzable con ejecución local previa o un helper no estándar.

En contraste, las cadenas de el daemon de portal cautivo, el daemon de autenticacion y redireccion y el servidor HTTP embebido demostraron ejecución de código verificada. La diferencia no es el CWE, es la cadena completa: ¿el código vulnerable es alcanzable desde donde puede estar un atacante, y eso se convierte en ejecución? Donde no hay cadena, no hay hallazgo de alto impacto.
