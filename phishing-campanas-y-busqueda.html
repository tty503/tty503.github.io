Campanas de phishing conectadas y el metodo de busqueda de amenazas: cuatro investigaciones

Redireccion multi-capa con exfiltracion a canales de mensajeria, una SPA con geofencing, y la bitacora de un ano de caza: mapa OSINT de una red de estafa, fraude con un stealer, un RAT comercial y un dropper multi-etapa. Lo que conecta las cuatro.

2026-05-2433 minThreat Intelligence

1. Resumen de Inteligencia

En junio de 2025 identifiqué dos campañas de phishing activas que, aunque utilizan stacks tecnológicos diferentes, comparten patrones de infraestructura y fuentes de datos que sugieren una conexión operativa o, como mínimo, un ecosistema de atacantes que reciclan las mismas listas de correos filtrados. Este artículo documenta ambas campañas, las correlaciona con investigaciones previas del portafolio y extrae patrones de threat intelligence aplicables a la detección proactiva.

La Operación General JP es una campaña de phishing multi-capa que utiliza Google Cloud Storage como punto de entrada, una cadena de redirección con dominios intermedios, y un kit PHP que exfiltra credenciales a través de la API de Telegram. La Operación SilentWarn es una campaña más reciente construida con React y Create React App, que utiliza EmailJS y SMTPjs para la exfiltración de datos, implementa geofencing para redirigir a usuarios vietnamitas, y está alojada en Cloudflare Pages.

Este artículo conecta ambos casos con investigaciones previas del portafolio: la Threat Hunter Recollection, la Operación FakeWealth, y la red de Pig Butchering bybsusd.com. El hilo conductor es la metodología: pivotar sobre infraestructura, leer los errores del adversario y correlacionar patrones a través de campañas aparentemente independientes. El análisis de estas campañas se realizó desde un entorno de investigación blindado con la infraestructura de túnel ofuscado con WireGuard y proxy residencial para evitar alertar a los operadores.

2. Operación General JP: Phishing Multi-Capa con Exfiltración a Telegram

Descubrimiento: URLs en Caché y Listas de Correos Filtrados

El punto de partida fue una lista de URLs en caché que compartían un patrón común, utilizando Google Cloud Storage como infraestructura de entrada. Todas las URLs seguían una estructura donde el parámetro user contenía direcciones de correo electrónico obtenidas de filtraciones masivas: 

// Patrón de URL identificado en caché
https://185.80.129.110/public/?:nav=unsuboffre::tracker
&deploy=2046847
&user=test%40correo.com
&email_id=147138100

La IP 185.80.129.110 está asociada a storage.googleapis.com. Al consultar los correos del parámetro user, confirmé que todos provenían de tres fuentes principales de filtraciones: logs de Alien Stealer, breaches de plataformas como Deezer, y combolists como Zacks2024. Este patrón —reutilizar bases de datos filtradas para alimentar campañas de spam— es consistente con lo documentado en la Threat Hunter Recollection (caso Rekrute y ShinyHunters), donde una filtración de datos se convirtió en el insumo para una operación de fraude masivo años después del breach original. La misma dependencia de datos filtrados aparece en la Operación FakeWealth, donde los atacantes usaban listas de correos comprometidos para alimentar sus campañas de spam financiero.

Cadena de Redirección Multi-Capa

El grafo de infraestructura mapea el flujo completo de redirección. El tráfico inicia en Google Cloud Storage y salta secuencialmente a través de múltiples dominios antes de llegar al destino final:

El generador de redirección dinámica utilizaba JavaScript para construir el siguiente destino en función de los parámetros de la URL. El parámetro encoded_value contenía un string en Base64 que, al ser decodificado, revelaba un identificador de campaña segmentado en varias partes: 

document.getElementById('button1').addEventListener("click", function(){
    var urlParams = new URLSearchParams(window.location.search);
    var encodedValue = urlParams.get('encoded_value');
    var domain = urlParams.get('domain');
    var sub1 = urlParams.get('sub1');
    var sub2 = urlParams.get('sub2');
    var sub3 = urlParams.get('sub3');
    var sub4 = urlParams.get('sub4');
    var sub5 = urlParams.get('sub5');
    window.location.href = "https://" + domain + "/cmp/" + encodedValue + "/JMMGSF/?source_id=" + ...
}, false);

Dependiendo del perfil de la víctima, el destino final variaba: algunos correos llevaban a una falsa página de FedEx, otros a un supuesto portal de noticias canadiense, y otros a una inmobiliaria fraudulenta cuya plantilla ni siquiera había sido modificada —los atacantes dejaron la URL de donde descargaron la plantilla original—. Si se omitía el parámetro, la redirección se frenaba y aparecía un mensaje emergente solicitando el parámetro faltante. Esto confirma que el sistema estaba diseñado para segmentar campañas por perfil de víctima usando el mismo backend.

El Servidor de Correo y Filemail API

Durante el análisis de las redirecciones, se identificó que el servidor de correo utilizado para el envío masivo de spam estaba impulsado por la API de Filemail (filemail.com). Los atacantes no utilizaban la API directamente, sino que ofuscaban los parámetros en strings segmentados y codificados que eran reconstruidos en tiempo de ejecución: 

// Estructura de la API de Filemail abusada por los atacantes
POST /api/transfer/complete
?logintoken=KDJF9JDF7JFN754H
&transferid=HGTUIJBGTRFGJPO
&transferkey=3783hf73h783jhdf83j93k

El último parámetro de la URL contenía el dominio con el que se disfrazaba el origen del correo (www.mechatecha1520.com), una técnica clásica de email spoofing para evadir filtros antispam. La URL intermedia contenía un extracto de la API de Filemail con todos los parámetros ofuscados en lugar de parsearlos directamente.

Lección de Threat Intelligence: Abuso de APIs Legítimas

El abuso de servicios legítimos —Google Cloud Storage para alojar el script de redirección, Filemail API para el envío de correos, IPFS para enmascarar la IP del servidor— es una constante en campañas modernas de phishing. Este patrón es consistente con lo documentado en la Operación FakeWealth, donde los atacantes abusaban de Cloudflare, Google Cloud y NameCheap como capas de protección. La diferencia aquí es que General JP añadió una capa adicional: un servidor intermedio en Lituania sin dominio que actuaba como punto de entrega de contenido malicioso y, posiblemente, de malware.

El Kit de Phishing "General JP"

Uno de los hallazgos más valiosos fue la recuperación del archivo reservigt.com/japangenerals.zip. El contenido reveló la estructura completa de un kit de phishing genérico pero funcional, bautizado internamente como "General JP". La siguiente captura muestra la interfaz renderizada del archivo de registro logins.html expuesto en el servidor del atacante, funcionando como una bitácora centralizada donde el script de backend volcaba secuencialmente las credenciales robadas:

El correo que inicia la cadena de esta campaña suplanta a Meta for Business, utilizando una técnica de ingeniería social basada en la urgencia y el miedo ante una supuesta infracción de propiedad intelectual:

El backend next.php era el núcleo del fraude. Su lógica interna realizaba tres acciones críticas: escribir las credenciales en logins.html —visible en la captura anterior—, enviar una alerta en tiempo real a través de la API de Telegram, y redirigir a la víctima al sitio legítimo para mitigar sospechas.

Mecanismo de Exfiltración Dual

El kit implementa dos canales de exfiltración: el archivo logins.html como almacenamiento persistente en el servidor —visible en la captura de la bitácora—, y la API de Telegram como canal de notificación en tiempo real. Si se encontrara un kit con el token del bot de Telegram activo —las variables $user_id y $botToken estaban vacías en la muestra recuperada—, se podría acceder a todo el historial de víctimas. Este patrón de exfiltración dual es consistente con kits de phishing documentados por Trustwave y Unit 42 en campañas similares.

3. Operación SilentWarn: Phishing en React con Geofencing Vietnamita

Descubrimiento y Vector de Entrada

Apenas unas semanas después de documentar General JP, un nuevo correo de phishing llegó a mi radar. El remitente era eogagnzgytatmtneaeseof@sell9proxy.com —un dominio registrado desde diciembre de 2024 a través de one.com, un proveedor económico de hosting— y el enlace utilizaba un acortador de Rebrandly: rebrand[.]ly/WebSite22fc63. La campaña tenía poco tiempo activa: la única referencia pública era una denuncia aislada de principios de junio de 2025.

Infraestructura Técnica: React + EmailJS + SMTPjs

El enlace acortado redirigía a silentwarn-2569-formsubmit-5g6h7j8k-entries-9c0d1e2f.pages[.]dev, un sitio alojado en Cloudflare Pages. El HTML inicial revelaba una aplicación construida con React (Create React App) que cargaba smtpjs.com/v3/smtp.js —un cliente SMTP incrustado directamente en el frontend— y utilizaba EmailJS como servicio de envío de correos para la exfiltración: 

<!-- HTML inicial del sitio SilentWarn -->
<!doctype html>
<html lang="en">
<head>
    <meta name="robots" content="noindex, nofollow"/>
    <title>Meta for Business | Privacy Center</title>
</head>
<body>
    <script src="https://smtpjs.com/v3/smtp.js"></script>
</body>

A diferencia de General JP —que utilizaba un backend PHP tradicional con exfiltración a Telegram—, SilentWarn apostaba por una arquitectura completamente basada en JavaScript: React para el frontend, EmailJS para el envío de correos, y SMTPjs como cliente SMTP incrustado. El sitio también implementaba un sistema de respaldo: si el servicio principal de EmailJS fallaba, automáticamente conmutaba a un servicio secundario con credenciales diferentes.

Geofencing: Protegiendo al Atacante Vietnamita

El hallazgo más revelador de SilentWarn fue el código de geofencing. La aplicación consultaba get.geojs.io/v1/ip/geo.json para obtener la geolocalización del visitante y, si detectaba que la IP provenía de Vietnam (VN), redirigía inmediatamente a Facebook: 

fetch("https://get.geojs.io/v1/ip/geo.json")
    .then((res) => res.json())
    .then((data) => {
        if (data.country_code === "VN")
            window.location.href = "https://www.facebook.com/";
    })
    .catch(console.error);

Esta técnica —redirigir a los usuarios del país de origen del atacante para evitar que sean víctimas de su propia campaña y, sobre todo, para proteger la infraestructura de ser analizada por investigadores locales— es un indicador de atribución consistente con actores de amenazas operando desde Vietnam. Los comentarios en vietnamita dispersos por el código fuente refuerzan esta hipótesis. Esta técnica de geofencing es conceptualmente similar a la que documenté en el análisis de la red de Pig Butchering, donde los atacantes redirigían a usuarios de ciertos países para proteger su infraestructura.

Adicionalmente, el sitio implementaba bloqueo de herramientas de desarrollo mediante un event listener que prevenía las teclas F12, Ctrl+Shift+I, Ctrl+Shift+J, Ctrl+Shift+C y Ctrl+U. También mostraba un splash screen de 6 segundos con un video a pantalla completa antes de cargar el contenido principal, una técnica de ofuscación para evadir análisis automatizados.

Flujo de Exfiltración: EmailJS + iplogger

El flujo de exfiltración de SilentWarn era más simple que el de General JP pero igualmente efectivo. La aplicación utilizaba EmailJS como servicio principal de envío, con un sistema de respaldo que conmutaba a credenciales secundarias si el servicio primario fallaba: 

const handleSendMailJs = (data) => {
    const primaryServiceId = process.env.REACT_APP_EMAILJS_SERVICE_ID;
    const primaryTemplateId = process.env.REACT_APP_EMAILJS_TEMPLATE_ID;
    const primaryPublicKey = process.env.REACT_APP_EMAILJS_PUBLIC_KEY;
    const backupServiceId = process.env.REACT_APP_EMAILJS_BACKUP_SERVICE_ID;
    const backupTemplateId = process.env.REACT_APP_EMAILJS_BACKUP_TEMPLATE_ID;
    const backupPublicKey = process.env.REACT_APP_EMAILJS_BACKUP_PUBLIC_KEY;
    // Intenta enviar por el servicio primario; si falla, conmuta al backup
    const apiUrl = process.env.REACT_APP_API_URL;
};

Los datos de la víctima se enviaban por correo a través de api.emailjs.com. Previamente, el sitio realizaba una captura de datos de geolocalización mediante un iplogger. La combinación de EmailJS como canal de exfiltración y SMTPjs como cliente de correo incrustado en el frontend representa una evolución respecto a los kits PHP tradicionales: toda la lógica de exfiltración reside en el cliente, lo que dificulta el rastreo del backend.

4. Correlación y Patrones entre Campañas

Aunque General JP y SilentWarn utilizan stacks tecnológicos diferentes —PHP con Telegram vs. React con EmailJS—, comparten patrones que las conectan dentro del mismo ecosistema de amenazas:

  • Fuente de correos: Ambas campañas utilizan listas de correos obtenidas de filtraciones masivas (Alien Stealer, combolists, breaches de plataformas).
  • Abuso de infraestructura legítima: Google Cloud Storage y Filemail API en General JP; Cloudflare Pages, EmailJS, SMTPjs y Rebrandly en SilentWarn.
  • Geofencing como mecanismo de protección: SilentWarn redirige a usuarios vietnamitas; General JP segmenta el destino final según el perfil de la víctima.
  • Exfiltración multicanal: General JP usa Telegram + archivo local; SilentWarn usa EmailJS primario + backup.
  • Pereza operacional: En General JP, los atacantes dejaron la URL de la plantilla original sin modificar y el archivo Untitled.png sin renombrar. En SilentWarn, los comentarios en vietnamita y las variables de entorno de EmailJS quedaron expuestas en el código fuente.

Patrón Transversal: Infraestructura Efímera y Reciclaje de Datos

Ambas campañas operan con infraestructura de bajo costo y alta rotación: dominios baratos (one.com), alojamiento en plataformas gratuitas (Cloudflare Pages, Google Cloud Storage), y servicios de exfiltración basados en APIs legítimas. Este patrón —infraestructura desechable alimentada por bases de datos filtradas— es el mismo que documenté en la red de Pig Butchering bybsusd.com y en la Operación FakeWealth. La diferencia es que estas campañas de phishing son más ágiles: se levantan en días, operan durante semanas y desaparecen cuando las listas de correos se agotan o los dominios son bloqueados.

6. Conclusión

Las operaciones General JP y SilentWarn representan dos caras del mismo ecosistema de phishing moderno: campañas ágiles, de bajo costo, que abusan de infraestructura legítima y reciclan bases de datos filtradas para maximizar el alcance. La diferencia técnica entre ambas —PHP tradicional vs. React con EmailJS— refleja la diversidad de stacks que los atacantes están adoptando, pero los patrones subyacentes son los mismos.

Para el threat hunter, la lección es clara: los IoCs específicos de cada campaña caducan rápido, pero los patrones de infraestructura —abuso de Google Cloud Storage, Cloudflare Pages, APIs de correo legítimas, geofencing para proteger al atacante, y reutilización de listas de correos filtrados— son atemporales. La detección proactiva debe pivotar sobre estos patrones, no sobre los dominios individuales.

Este artículo se suma a la serie de investigaciones documentadas en la Threat Hunter Recollection, conectando casos de phishing con fraudes financieros, Pig Butchering y campañas de malware. El hilo conductor sigue siendo el mismo: la infraestructura es el talón de Aquiles del adversario.

    10. Mapeando una red de estafa piramidal global

    Todo empezó con un mensaje que no pedía nada raro: un número sudafricano ofrecía dinero por «clasificar hoteles en Google Maps». Sospeché de inmediato, lo seguí hasta el final y fui publicando lo que encontraba en tiempo real en X. Aquella curiosidad destapó una operación de estafa piramidal de alcance global, con tentáculos en apuestas fraudulentas, exchanges falsos y robo de identidad corporativa. Fue mi bautismo de fuego en OSINT aplicado a threat hunting.

    Task scams: el contexto global

    Las estafas de tareas son una plaga con cifras oficiales encima: según la FTC, solo en EE.UU. este formato provocó pérdidas cercanas a los 220 millones de dólares durante el primer semestre de 2024. El guion nunca cambia: primero pagan micropagos para ganarse tu confianza; después exigen una «inversión» que jamás regresa. Lo que distingue a estas variantes es su disfraz perfecto de oferta legítima de teletrabajo.

    El vector de ingeniería social: WhatsApp, Telegram y un falso CEO

    El contacto inicial llegó desde el número +27610596209, en Sudáfrica, un país cuyo mercado de SIM swapping medios como MyBroadband han señalado repetidamente como problemático. Por WhatsApp, con un español impecable, la víctima era informada de que «acababa de ser seleccionada para un empleo», alegando haber hallado su perfil en Rekrute, una plataforma de empleo francesa perfectamente legítima que había sufrido filtraciones previas.

    Superada la primera tarea de clasificación hotelera, entregaban un código para ascender de fase: pasar a hablar con la «Asistente» y el «CEO» por Telegram. Ahí estaba el salto de confianza: del chat informal de WhatsApp a la escenografía corporativa falsa montada en Telegram.

    Al examinar el perfil del «CEO» los detalles se fueron apilando solos. El logotipo de la empresa inventada, WTNBIT, pertenecía en realidad a Poloniex Exchange, rebautizado sin más. A las víctimas les prometían pagos en USDT mediante «su plataforma»: un exchange falso construido por ellos mismos.

    Los primeros movimientos de dinero corrían por bancos nacionales con importes pequeños, suficientes para construir confianza. Después llegaban las promesas de ganancias desorbitadas, siempre empujando a depositar en su plataforma de «exchange»; y una vez dentro, el dinero simplemente dejaba de existir. Era un esquema ponzi vestido de empleo remoto donde, en las rondas iniciales, eran las propias víctimas quienes pagaban a las víctimas.

    La revelación: infraestructura reciclada y pereza operacional

    Al abrir el código fuente de la plataforma fraudulenta alojada en vcimp[.]h21t[.]top me encontré con un nivel de vagancia casi insultante. No había producto: había una plantilla HTML mal configurada reciclada para distintas marcas de fraude. Las mismas referencias a canales de Telegram, los mismos servicios de imágenes genéricos (picsum.photos) y las mismas hojas de estilo Bootstrap maliciosas servidas desde lib.sinaapp.com delataban un único grupo detrás de todas las operaciones.

    No ofuscaron absolutamente nada, así que recolecté datos sin resistencia. Di con otra copia del mismo exchange falso, algo más pulida estéticamente pero calcada en estructura, esta vez con el idioma por defecto en indonesio. El denominador común de todas ellas: hosting en Hong Kong.

    ⚠ Comparativa con la industria: task scams y SIM swapping

    Investigadores de DomainTools y ThousandGuards ya habían descrito cómo el clipboard poisoning y páginas CAPTCHA falsas sirven de vehículo para entregar malware como NetSupport RAT en campañas de task scams. Mi hallazgo aporta un matiz adicional: la misma plantilla reciclada sirve tanto para distintas víctimas como para distintos nichos de fraude (phishing laboral, crypto scam, apuestas ilegales). Esa transversalidad delata grupos criminalmente diversificados que explotan varias líneas de negocio ilícito sobre una sola columna vertebral técnica.

    El pivote con VirusTotal Graph sacó a la luz una infraestructura sorprendentemente amplia y sorprendentemente mal cuidada: series consecutivas de dominios clonados (www.vcimpapp1.com hasta www.vcimpapp32.com) resolviendo a IPs de Hong Kong con un error de base de datos MySQL expuesto a cualquiera.

    La conexión con ShinyHunters y la filtración de Rekrute

    ¿Por qué justo Rekrute? Porque esa plataforma francesa de empleo arrastraba una filtración masiva de años atrás: entre las bases de datos que ShinyHunters filtró —y después vendió— en el mercado negro Empire figuraba precisamente la de Rekrute. Los estafadores no eligieron esa marca por azar: disponían de una base de personas buscando activamente empleo remoto, el cliente ideal para un task scam.

    El grafo de VirusTotal dejaba además un vínculo directo con ShinyHunters, citando coberturas de Cybernews, ZDNet y SecurityAffairs sobre sus filtraciones. La base comprometida que alimentaba el contactado de víctimas demostraba en la práctica cómo un breach puede convertirse en materia prima de fraudes masivos meses o incluso años después. Ese mismo patrón de fugas de información sobre infraestructura descuidada es el que crucé en la Operación FakeWealth contra cmdxcapital, donde un appDebug:true en Laravel exponía consultas SQL, tokens y rutas internas del servidor.

    ✕ Conexión con ShinyHunters

    Cruzar actores de amenaza con fraudes posteriores es, en esencia, el trabajo diario de un Threat Hunter: unir puntos que otros perciben como islas. La filtración de Rekrute no fue solo una pérdida de datos; fue el combustible de una operación de fraude aún viva mucho tiempo después del breach. Comprender el ciclo completo del dato filtrado —del robo a la monetización— es una competencia crítica de threat intelligence.

    La vulnerabilidad reveladora: OpenSSH 7.4

    Varios servidores de la red compartían una misma tarjeta de presentación: OpenSSH 7.4, la versión publicada en diciembre de 2016 y cargada de CVEs conocidos. Al principio pareció una coincidencia irrelevante —servidores hongkoneses mezclando apuestas, exchanges falsos y portales de empleo trucho—, pero ese detalle técnico común confirmó lo obvio: una sola mano administraba todo. Aunque el fallo asociado se limitaba a enumeración de usuarios sin acceso remoto, la huella versional bastó para coser la red.

    Además compraban dominios a través de un servicio barato de reventa que aceptaba Bitcoin y USDT. Cuatro sitios del diagrama, cuando menos, compartían idéntico index.html: una plantilla genérica apuntando al mismo backend y saludando al mismo canal de Telegram. Sitios aislados, ninguno. La misma gente cambiándose el nombre.

    ⚠ Lección aprendida: las migas de pan del adversario

    Los ciberdelincuentes reciclan infraestructura y, al hacerlo, dejan rastro. Una consulta de Shodan por versión de OpenSSH, un vistazo al código de una plantilla o la correlación de canales de Telegram entre dominios pueden desnudar una red entera. La pereza operacional del adversario es el mejor aliado del cazador. El grafo completo está publicado en el post original de LinkedIn y el relato en vivo quedó en el hilo de @tty_503.

    De este caso salió la idea que gobierna todos mis análisis posteriores: la infraestructura es el talón de Aquiles del adversario. Pivotar entre dominios, IPs, versiones de software y canales de Telegram no exige sofisticación alguna; exige curiosidad aplicada con método. Y funciona.

    11. Exponiendo una campaña multi-vector de fraude financiero

    Semanas después de cerrar el caso piramidal, un cabo suelto en Telegram me condujo hacia una operación de otra liga. Aquí tocó aprender análisis de infraestructura comprometida y rastreo financiero sobre blockchain por las malas: siguiendo el dinero.

    El combustible: Lumma Stealer

    El detonante fue un compromiso masivo de credenciales corporativas firmado por Lumma Stealer, un infostealer que se comercializa bajo modelo Malware-as-a-Service (MaaS). Su peligrosidad extra reside en que no se conforma con contraseñas: captura tokens 2FA y cookies de sesión, ampliando el radio de daño mucho más allá de un simple volcado de credenciales.

    En mayo de 2025 una operación internacional incautó 2.300 dominios de Lumma y dejó el ecosistema cojeando. Pero el MaaS demuestra una resiliencia notable: para julio de 2025 ya se detectaban signos de reactivación. Más tarde, Gen Threat Labs documentaría Remus, la variante de 64 bits de Lumma aparecida en febrero de 2026 e incorporando técnicas como EtherHiding para resolver sus C2.

    ⚠ Lección de threat intelligence

    Los takedowns duelen pero no matan. Lumma sobrevivió a perder 2.300 dominios porque su negocio —desarrolladores alquilando el malware a una red mundial de afiliados— no cuelga de ninguna infraestructura fija. Para un Threat Hunter esa lectura del modelo económico del adversario es tan necesaria como bloquear IoCs: sin ella, solo estás jugando al whack-a-mole.

    BEC e infraestructura robada en África

    Con las credenciales en la mano, los atacantes montaron un Business Email Compromise (BEC) apoyado en servidores de terceros comprometidos. Su escondite elegido: una VPS en Kenia con actividad visible en Truehost Cloud y Cloudpap.

    Escoger jurisdicciones con marcos regulatorios laxos no es casualidad ni mala suerte: es patrón. Diversas investigaciones de la industria coinciden en que los actores buscan países donde el derribo de un servidor cuesta semanas en lugar de horas.

    Siguiendo el dinero en la blockchain

    La fase de cobro pasaba por billeteras cripto. La dirección Bitcoin bc1qxs8aunxd7kkdq8wz063r4tum2429s5llul33am registró movimiento entre el 8 y el 9 de septiembre de 2025. Esa destreza de blockchain forensics —leer transacciones sobre redes públicas para reconstruir patrones de fraude— es de las más solicitadas hoy en threat hunting, especialmente en ransomware y fraude financiero.

    ✕ Ciclo de ataque documentado

    Lumma Stealer (credenciales) → BEC (infraestructura robada) → Crypto Scam (monetización). Este encadenamiento demuestra que detrás de un scam aparentemente burdo puede latir una operación seria de robo de activos corporativos. Publiqué los IoCs completos en el post original de LinkedIn.

    12. Diseccionando Nexilo-CC-Checker: un dropper multi-etapa

    El tercer caso me metió de cabeza en el reversing de malware. Un binario de 14.4 MB que circulaba por canales de Telegram vendido como herramienta de carding resultó ser un dropper multi-etapa capaz de desplegar un arsenal de seis payloads distintos.

    Técnicas de evasión: API Hashing

    Para esconder llamadas delicadas como IsDebuggerPresent, el binario recurrió a API Hashing: en lugar de declararlas en la tabla de importaciones, las resolvió en runtime mediante hashes —con la constante 0x2b992ddfa232 cargada en RAX— sin dejar cadenas reconocibles al análisis estático. Es una de las primeras murallas que todo analista aprende a saltarse, y Hasherezade la tiene documentada en profundidad. Mi compendio de técnicas de inyección y evasión del C2 Builder describe el mismo mecanismo desde la trinchera ofensiva: cómo se arma el API Hashing para burlar firmas estáticas.

    La función FUN_140001010 marcaba el punto de no retorno de todo el dropper.

    La armada de payloads y la persistencia

    El dropper sembraba seis payloads en AppData\Roaming con atributos OCULTO + SISTEMA y nombres calcados de procesos legítimos. Para sobrevivir al reinicio, se anclaba en la clave Run del Registro.

    ⚠ Comparativa con Maltiverse

    La consulta posterior en Maltiverse ratificó la clasificación maliciosa y vinculó la muestra a familias como Xworm, Svcstealer y Stealc, con actividad de red atribuible a RedLine Stealer y MetaStealer. Que mi reversing manual converja con las detecciones automatizadas valida el análisis y subraya por qué conviene combinar ambas aproximaciones en lugar de elegir una.

    13. Detrás de cámaras: automatizando el triage con herramientas propias

    Analizar Nexilo-CC-Checker no fue sentarse a mirar. Con API Hashing de por medio, al binario hubo que arrancarle los secretos a la fuerza. Esa batalla es exactamente la que me enseñó a automatizar el triage con herramientas hechas en casa.

    El búnker: Proxmox VE

    Todo análisis de malware con capacidades de evasión empieza por decidir dónde pelear. Yo trabajo sobre Proxmox VE: snapshots al instante, rollbacks limpios y aislamiento total. Ese mismo laboratorio queda descrito en la guía de infraestructura ofuscada con WireGuard y proxy residencial que sostiene todas mis investigaciones.

    Forzando la mano: dump.sh

    Escribí dump.sh, un script Bash que orquestaba la ejecución del binario bajo depuración con Radare2 para volcar memoria de forma automática. El script se apoyaba en functions_to_dump.txt, un listado con las direcciones virtuales de memoria mapeadas módulo a módulo.

    analystty: la navaja suiza personal

    Con los dumps sobre la mesa, Ghidra hizo el trabajo de decompilar a pseudo-C. Pero la verdadera palanca fue analystty, mi librería Python nacida originalmente para estudiar el ransomware Djvu y readaptada aquí para acelerar la detección de patrones maliciosos. La filosofía cabe en una frase: que la máquina haga lo repetitivo y el criterio humano quede para lo que de verdad importa.

    ⚠ El valor de las herramientas propias

    En un mundo donde IDA Python y el scripting de Ghidra marcan el ritmo, construir tu propia herramienta como analystty acredita algo más grande que saber usar software: la capacidad de resolver problemas de análisis escribiendo código. Esa skill está desarrollada a fondo en analystty: automatizando el triage de malware PE con Python, Capstone y x64dbg, y es justo la línea que separa a quien usa un arsenal de quien sabe fabricarlo.

    14. Deconstruyendo NetSupport RAT: la kill chain completa

    El quinto caso fue el más redondo en cuanto a análisis de kill chain: desde el correo de phishing hasta la conexión con el C2, sin saltarme ni un eslabón de la cadena de infección.

    Contexto global de NetSupport RAT

    NetSupport Manager cerró 2024 como la séptima amenaza más prevalente. Cybereason documentó campañas repartiéndolo desde sitios WordPress con CAPTCHAs falsos, y ThousandGuards identificó combinaciones de clipboard poisoning con PowerShell ofuscado. Mi investigación se inscribe en ese contexto global pero suma un vector concreto: la suplantación de una marca española (Druni) respaldada por infraestructura nigeriana.

    Evasión y redirección

    El enlace del correo conducía a un script hreflon.htm hospedado en Google Cloud Storage, abusando de la reputación de servicios de confianza para colarse ante SmartScreen. Apoyarse en nube legítima para servir carga hostil es una tendencia que ya han documentado múltiples investigadores.

    El dominio de relevo gremorygame[.]net exhibía un inocente «Coming Soon» mientras el backend tramitaba la lógica maliciosa. Tapar la infraestructura tras fachadas inofensivas es un recurso que reaparece una y otra vez en campañas con oficio.

    PowerShell ofuscado y DLL Sideloading

    El script file.ps1 apostó por ofuscación simple pero suficiente: trocear cadenas como 'iw'+'r' para recomponer Invoke-WebRequest en memoria. El payload final ejecutó DLL Sideloading contra el ejecutable legítimo client32.exe de NetSupport Manager.

    La kill chain visualizada

    El diagrama final cosecha todos los hallazgos en una sola imagen de la cadena de infección. Contar el ataque entero de un vistazo —esa aptitud de comunicar técnica de forma visual— es la que permite llevar inteligencia accionable a respuesta a incidentes y a direcciones que no van a leer un hexdump en su vida.

    15. El hilo que lo conecta todo: el perfil del Threat Hunter

    Cinco casos, cinco vectores diferentes y un único denominador: la metodología. Si esta crónica prueba algo, es que un Threat Hunter no se decreta con certificaciones ni titulares: se consolida acumulando habilidades en el laboratorio y poniéndolas a prueba frente al adversario de verdad.

    Cada investigación fue un escalón en la escalera que hoy define mi perfil:

    • OSINT & Infrastructure Mapping — desarmar la red piramidal —del número sudafricano a los servidores hongkoneses con OpenSSH 7.4— me entrenó a pivotar sobre cada miga que deja el atacante.
    • Threat Intelligence & Blockchain Forensics — la campaña BEC me obligó a entender el ecosistema MaaS, seguir transacciones on-chain y conectar a ShinyHunters con fraudes financieros aún en marcha.
    • Ingeniería Inversa & Análisis de Malware — abrir en canal Nexilo-CC-Checker me dio el reverso estático y dinámico, de Ghidra al volcado de memoria con Radare2.
    • Automatización & Desarrollo de Herramientas — escribir dump.sh y analystty probó que puedo crear mi propio arsenal, no solo disparar el ajeno.
    • Análisis de Kill Chain Completa — reconstruir NetSupport RAT del phishing al C2 me enseñó a narrar un ataque entero, de la ingeniería social a la persistencia.
    ▣ Por qué este perfil es relevante

    El threat hunting va mucho más allá de encontrar malware: consiste en enlazar puntos que otros ven separados. En entender que un teléfono sudafricano, una VPS keniata, un dropper en Telegram y un correo suplantando a Druni pueden pertenecer al mismo rompecabezas. En asumir que los IoCs caducan mientras las TTPs permanecen. En poder construir la herramienta cuando ninguna existente alcanza.

    Frente a un ecosistema donde los actores mutan más deprisa que las defensas —Lumma esquivando takedowns masivos, NetSupport migrando al clipboard poisoning, task scams ramificándose hacia el criptofraude—, las organizaciones necesitan cazadores que no solo manejen herramientas, sino que comprendan al adversario.

    Esta recopilación es mi prueba. No pretende ser currículum: es el cuaderno de bitácora de alguien que sigue aprendiendo, construyendo y documentando. Porque la inteligencia de amenazas guardada en silencio es apenas un archivo en un disco; la que se contextualiza y comparte se convierte en blindaje para toda la comunidad.

    El laboratorio sigue encendido. Los canales de Telegram siguen vigilados. Las muestras siguen entrando. La crónica continuará.
